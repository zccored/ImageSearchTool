## 3. 黑名单：**不要再试**（已证伪，均有数据）
1. **加权准入信号量 / 大图物理双池** —— 仿真 B=108 墙钟 +59%
2. **`cv2.setNumThreads(2)`** —— 配对复跑真实效应 ≤1%（首测 −11.7% 是噪声）
3. **交叉引用**（libdeflate inflate + stored 重封装 + cv2）—— 0.63×
4. **GDeflate / nvCOMP** 用于本图库 —— 外来 IDAT 0/48 可解
5. **大图 RGB 也走旁路** —— 全库 CPU 降但墙钟 +3.1%（净负）
6. **zlib-ng / imagecodecs / Pillow 换 PNG 库** —— 1.16× / 0.84× / 0.74×
7. **nvJPEG 加速** —— 比 CPU cv2 更慢
8. **"长尾导致解码池打不满"** —— 池实测 15.47 核，建库 7.52 核是解码只占一部分
9. **progressive JPEG 拖慢** —— 全库只有 3.7% 渐进（旧记的"样本 0%"是抽样偏差），不构成主要因素
10. **换 JPEG 解码器（TurboJPEG / imagecodecs / mozjpeg）** —— 解码级 TurboJPEG 1.125× 且逐位一致，
    但建库级配对 A/B 稳定 **+20~22.5% CPU / +24~29% 墙钟**（净负，三次复跑同向）；
    imagecodecs / mozjpeg 因不支持 DCT 缩放解码只有 0.88×。
    要重开这条线，**必须先用持久句柄的 ctypes 绑定替掉 PyTurboJPEG 的每张 init/destroy** 再复测建库级
11. **更激进的 DCT 缩放阈值（>1600 就 1/2）** —— 实测**只省 15 核秒（0.26% 建库 CPU）**，
    却要重建全库索引并重跑召回；像素少 4 倍只快 1.42×（缩放的收益在输出侧，不在熵解码）
