## 2. 性能影响评估

### 2.1 方法（可复现）

用 `git worktree` 把**改动前的 HEAD（`1d97c07`）**单独取出到临时目录，与当前工作区在**同一台机器、
同一份样本数据**上对拍：

```bat
git worktree add %TEMP%\ise_ab\head HEAD
python -E make_test_dataset.py --out %TEMP%\ise_ab\data --db 300 --per-group 4 --queries 6

:: 改动前（在 worktree 里跑 HEAD 的 CLI）
cd %TEMP%\ise_ab\head
python -E main.py build      %TEMP%\ise_ab\data\db --prefix %TEMP%\ise_ab\idx\head_whole --limit 300
python -E main.py build-tiles %TEMP%\ise_ab\data\db --prefix %TEMP%\ise_ab\idx\head_tiles --limit 150

:: 改动后（在仓库里跑当前 CLI）
cd <仓库根>
python -E main.py build      %TEMP%\ise_ab\data\db --prefix %TEMP%\ise_ab\idx\now_whole --limit 300
python -E main.py build-tiles %TEMP%\ise_ab\data\db --prefix %TEMP%\ise_ab\idx\now_tiles --limit 150
```

样本：模拟图库 294 张入库（75 组近重复）；测试机 = **AMD RX 6700 XT + `torch 2.14.0+cpu`（纯 CPU 口径）**
—— 所以下面的绝对秒数是 CPU 基准，与 `docs/perf-plan.md` 里 NVIDIA 机器的数字**不可直接比较**，
只看**同一台机器的前后差异**。

### 2.2 建库吞吐（3 次采样，墙钟秒）

| 场景 | 改动前（HEAD） | 改动后（当前） | 判断 |
| :--- | :--- | :--- | :--- |
| 整图全量建库 300 张（融合单遍解码 + ResNet） | 15.9 / 13.2 / 12.8 → **中位 13.2** | 13.4 / 11.8 / 12.3 → **中位 12.3** | 差异 0.9 s（≈7%），**落在首轮冷启动与运行噪声内** |
| 瓦片建库 150 张 | 17.6 / 15.1 / 13.0 → **中位 15.1** | 15.9 / 13.3 / 12.5 → **中位 13.3** | 差异 1.8 s（≈12%），同样在噪声内（瓦片路径本身方差大） |

> 结论：**建库吞吐无回归**。数值上"改动后略快"，但两组区间（12.8–15.9 vs 11.8–13.4）本就重叠，
> 单机 3 次采样不支持"变快"的结论 —— 本次只主张"没变慢"。
> 另外一个可解释的小差异：改动后 CLI 默认写**侧车 `.npy`**（8 个小文件），改动前写 **npz**（单容器），
> 两者写盘成本接近，不构成系统差异。

### 2.3 索引内容一致性（**这是最强的"算法未变"证据**）

对同一份样本、同一组参数，逐数组比对改动前后产出的索引：

| 数组 | 结果 |
| :--- | :--- |
| 整图 `paths`（294 条路径） | ✅ **逐位一致** |
| 整图 `hu`（294×7） | ✅ **逐位一致** |
| 整图 `fp`（294×512 二值指纹） | ✅ **逐位一致** |
| 整图 `md5s` | ✅ **逐位一致** |
| 瓦片索引 150 行 | ✅ 行数相同、按「原图路径 + 框」建键后**键集合一致**、**同键指纹逐位一致** |
| `meta.cfg` 差异 | 仅 **`png_decoder`：`cv2` → `libdeflate`**（§3.1 的修正）；存储容器 `npz` → `sidecar`（同一批参数，`fast_load` 修正的直接后果） |

> 也就是说：**同一批输入，改动前后产出的索引在数值上完全等价**，差异只在"meta 里记的解码器口径"
> 与"存盘容器"这两件事上。

### 2.4 检索延迟（整图索引，Top-10，3 次）

| 版本 | 粗筛 | 精排 | 合计 |
| :--- | :--- | :--- | :--- |
| 改动前（npz 索引） | 28.4 / 26.4 / 29.6 ms | 4066.9 / 4518.0 / 4179.8 ms | 4095.4 / 4544.4 / 4209.5 ms |
| 改动后（sidecar 索引） | 28.6 / 26.6 / 33.2 ms | 4318.5 / 4138.4 / 4288.0 ms | 4347.0 / 4165.1 / 4321.3 ms |

- **粗筛（纯算法部分）逐次同量级**（26–33 ms），说明扫描/打分路径未变；

  差别最大的部分，本机（无 CUDA）无法代表你的机器。

## 3. 行为变化（**这部分需要你确认**）

### 3.1 CLI 建库的 meta 与存储格式，现在与 GUI / Web 一致

改动前 `cli.py` 里两个参数的 argparse 默认值会**覆盖** `Config` 默认值：

| 参数 | 改动前 | 改动后 | 后果 |
| :--- | :--- | :--- | :--- |
| `--png-decoder` | argparse 默认 `"cv2"`，被当成"显式传参"写进 `Config` → 建库 meta 记 `cv2` | 默认 `None` = **不覆盖**（用 `Config` 的 `libdeflate`） | meta 口径与 GUI/Web 一致 → `stats`/`compact`/`bench` **终于能打开 CLI 建的索引** |
| `--fast-load` | `store_true`，不传也被写回 `False` → CLI 建库写 **npz** | 只有显式传参才覆盖 | CLI 建库现在写 **侧车 `.npy`**（可 mmap：打开更快、常驻更省），与 GUI/Web 一致 |

> **为什么必须修**：改动前 `build` 写的 meta 是 `cv2`，而 `stats`/`compact`/`bench` 不注册 feature 参数
> → 取 `Config` 默认（`libdeflate`）→ 打开索引时一致性校验直接拒绝（rc=2）。
> 也就是说：**改动前 CLI 建的索引，CLI 自己读不了**（已在 HEAD 版本上复现：rc=2）。
> 现在三入口（GUI / Web / CLI）默认完全一致。

### 3.2 索引兼容矩阵（今天实测）

| 索引由谁建 | meta `png_decoder` | 存储 | 新 CLI `stats`/`compact` | 新 CLI `search`/`add` | GUI / Web |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **旧 CLI**（≤ `1d97c07`） | `cv2` | npz | ✗ **rc=2**（无 feature 参数可传，见 §3.3） | ✅ 加 `--png-decoder cv2` 即可（实测：`search` 命中正确、`add` rc=0「无新增图片」） | ✗（GUI 也按 `libdeflate` 基准，属既有行为） |
| **新 CLI / GUI / Web** | `libdeflate` | sidecar | ✅ **rc=0** | ✅ 不用加任何开关 | ✅ |

- **npz 容器本身没被废弃**：新 CLI 照旧能读 npz（上表第 5 列已验），只是"meta 里的解码器口径"必须匹配；
- 所以你手上**旧的 CLI 建索引**有三条路：① 查询/增量时显式加 `--png-decoder cv2`；
  ② 直接 `build --force` 重建（推荐：顺便升级成侧车）；③ 若打算长期用，也可以把 meta 口径统一后再继续。

### 3.3 遗留（本次**没做**，需要你决定）

`stats` / `compact` / `bench` 这三个子命令**没有注册** feature 参数（`--png-decoder` 等），
所以它们**无法**显式声明"我要按 cv2 基准打开"。对 `cv2`-meta 的老索引，它们会一直报
「当前参数与建库参数不一致」而拒绝打开（rc=2）。

- 这是**既有设计**（不是本次引入）：改动前同样如此；
- 两条可选修法，都超出"修既有缺陷"的范围，故留给你定：
  1. 给这三个子命令也 `_add_feature_args()` → 用户可显式声明基准；
  2. 一致性校验对**只读命令**（`stats` 只读 meta、`compact` 只做格式转换）放宽 `png_decoder` 这一项。

### 3.4 日志不再"吞掉结尾"

`cli.py` 退出前会 `drain_stderr_noise()`，日志输出流改为"真终端代理"（不再写进 PNG 噪音过滤的管道）。
改动前：进程退出时**最后几行日志（往往就是报错正文）会消失**，只看到 INFO 行 + 退出码 2；
现在错误正文能正常打出来（实测见 §4）。噪音过滤能力未变（51 行噪音被吞 / 1 行真实告警透出）。

### 3.5 界面侧（不影响算法）

- **`gui.py` 保留但降为"保底"**：编排逻辑迁到 `service.py`（净 −352 行），后续以缺陷修复为主；
- **新增 Web 版**：独立 exe，进程内 `js_api` 调服务层（不经 HTTP），HTTP 段只读且只监听回环；
- **布局（2026-09-27 追加）**：系统窗口标题已写着产品名 → **页内不再重复标题**（页头那一行整个删掉，
  页面直接从工具栏开始）；运行状态徽标（`空闲` / `处理中…`）**移到窗口底部状态栏左侧**
  （中段是任务状态文字、右侧是通道状态）→ 少占一行、产品名只出现一次；
- **亮/暗色主题（2026-09-27 追加）**：页签行右端新增切换按钮（按钮文字＝点它会切到哪个）；
  选择存 `localStorage['ise.theme']` 并记住；实现是 `src/theme.js` + `theme.css` 的两套变量
  （`:root` 暗色 / `:root[data-theme="light"]` 亮色），**组件样式已全部改为走变量**；
  真窗口回归里新增 **Gate 6**：断言两套配色确实生效（body 背景色不同）+ 点击即切；
- **窗口标题现在可配置**：`gui_web.py` 读外置 `ui_strings.json` 的 `app.title`（缺省回落内置），
  所以删掉页内标题**不会**让标题变得不可改 —— 依然不用 Node、不用重新打包；
- **免 Node 维护**：包根放 `ui_strings.json`（文案 + 窗口标题） / `ui_theme.css`（**亮/暗两套分别写**）即可覆盖，改布局才需要 `pnpm build`；

## 5. 建议你在 NVIDIA 机上复测的清单

按"必要性"排序（前 3 条能在 10 分钟内给出你真正关心的数字）：

1. **真实图库整图 / 瓦片全量建库**，与 `docs/perf-plan.md` §一 的
   `483.8 s`（整图）/ `1033.6 s`（瓦片，09-26 口径）对比 —— 这才是你关心的性能数字；
   命令：`python -E main.py build <图库根> --prefix <图库根>\.gallery_index\gallery`（瓦片同理 `build-tiles`）。
2. `python -E devtools/verify_service.py` + `python -E devtools/verify_web_gui.py`（真窗口）
   —— 判据都是「结果: 全部通过」，用来确认在 CUDA 路径上服务层/界面没有你机器特有的问题。
3. `python -E main.py bench <目录> --limit 500 --fine-sample 64` —— GPU 精排吞吐与检索延迟。
4. `python -E devtools/verify_gui_perf.py`、`verify_thumb_perf.py`（需桌面会话 + 真实图库）
   —— tkinter 保底界面的构建/首屏/内存回归（脚本里改一下硬编码路径）。
