# CPU/GPU 双路同源：10,000 张 A/B + 帧交错分析

> 数据：`results/dual_path_10k.json`、`results/frame_interleave_stats.json`
> 图：`results/fig_frame_interleave.png`（帧交错）、`results/fig_dual_path.png`（1k 对比）
> 前提：游戏已退出、10k 磁盘缓存预热、按对交错（PIL→GPU、GPU→PIL 交替）抵消热漂移。

## 1. 10k A/B 结果（4 对配对）

| 配对 | PIL | torch-GPU | 差异 |
| :--- | ---: | ---: | ---: |
| P1 | 108.78 s | 96.79 s | **−11.0%** |
| P2 | 121.84 s | 100.28 s | **−17.7%** |
| P3 | 122.75 s | 105.31 s | **−14.2%** |
| P4 | 122.35 s | 104.96 s | **−14.2%** |
| 均值 | 118.93 s | **101.84 s** | **−14.3%** |

- 每对都是 GPU 更快，方向一致；PIL 后段 122 s 是热漂移，GPU 后段 105 s 也同步变慢，配对后差异仍 −14%。
- 1k 测得的 −10.9% 在 10k 扩大到 **−14.3%**，说明规模越大 GPU 车道收益越明显。

## 2. 钩子开销（HERMES_TRACE）

| 运行 | 墙钟 |
| :--- | ---: |
| 未追踪 GPU（同时段） | 105.48 / 105.92 s |
| 追踪 GPU（轻量元组） | 103.70 / 104.49 s |

追踪版**不比同时段未追踪慢**（差异在热漂移噪声内），且默认关闭（`HERMES_TRACE` 未设置时零开销：仅每图一次属性判空）。

## 3. 帧交错（10k GPU 建库，追踪 9999 张）

| 指标 | 值 |
| :--- | ---: |
| 追踪跨度 | 101.6 s |
| GPU 前向忙碌 | **17.9%**（空闲 **82.0 s**） |
| GPU 批间空隙 p50 / p90 | **1.61 s / 3.04 s** |
| 前向耗时 p50（256 张/批） | 288 ms |
| 批间等待 p50 / p90 | 3.7 / 10.1 ms |
| 解码线程占用率（20 线程） | 33.2% |
| 单图解码 p50 | 17.8 ms |
| 单图预处理尾段 p50（GPU resize + 往返） | 17.9 ms |

**可调度位置（按收益排序）**：

1. **批量化 GPU 预处理**：当前 20 个线程各自对单图做 H2D + resize + D2H，GPU 上串行化，
   单图尾段 17.9 ms；改成每 8–16 张一次上传/一次 resize，可把这部分压到 2–4 ms/张。
2. **在 GPU 前向的空隙里预取下一批**：空隙 p50 1.6 s，足够把下一批 256 张的 RGB 上传并预处理，
   前向结束后直接吃现成张量，等于把预处理完全藏进空隙。
3. **CPU 侧**：解码线程只有 33% 占用，说明大量时间在等 GPU 尾段/队列；把预处理移出解码线程后，
   解码可恢复到接近满核（当前 12.3–13.0 核 / 20）。

## 4. 结论

- 10k 规模 **−14.3% 墙钟**，且 GPU 仅 18% 忙碌、空隙 1.6–3 s，**还有明显可挖空间**。
- 下一步实现"批量化 GPU 预处理 + 双车道调度"（CPU 解码 + GPU 批量预处理/前向，队列满回退），
  预期可从 −14% 推到 −20% 以上；需先做 1k 原型验证语义与内存，再上 10k。
- 追踪钩子不影响性能，可保留为诊断开关。

## 5. 批量化 GPU 预处理 + 全量实测（2026-10-30 晚）

### 实现

| 位置 | 改动 |
| :--- | :--- |
| `config.py` | `prep_batch`（默认 8）、`prep_px_budget_mp`（预留） |
| `prep_torch.py` | 新增 `transform_to_device()`：同一套 resize/crop，结果留在 GPU |
| `fine.py` | 新增 `ResNetExtractor.forward_rgb()`：单线程批量做 H2D + resize/crop + 一次前向；记录 `last_times` |
| `engine.py` | `prep` 在 `prep=="torch" and prep_batch>0` 时只返回原始 RGB；`on_batch` 识别 numpy 后走 `forward_rgb` |
| `engine.py`（追踪） | 轻量元组追踪（默认关），新增 `("batch", t0, rgb_prep, fwd, n)` |

### 单图预处理尾段

| 方式 | 单图耗时 |
| :--- | ---: |
| 20 线程各自 H2D+resize+D2H（旧） | **17.9 ms** |
| 单线程批量预处理（新） | **3.69 ms** |

### 批量大小选择（1k）

| batch | 墙钟 | RSS |
| ---: | ---: | ---: |
| 32 | 10.25 s | 2369 MB |
| **64** | **8.92 s** | 2977 MB |
| 256 | 10.36 s | 5699 MB |

batch=256 时原始 RGB 在队列里堆积（队列深度 3 × 256 × 6.5 MB ≈ 5 GB），全量首次尝试直接 **582 s / RSS 10.6 GB**（换页）；降到 64 后恢复正常。

### 全量真实图库（37,682 张，同机同日对照）

| 路径 | 墙钟 | 吞吐 | CPU 核数 | GPU 利用率 | RSS 峰值 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| PIL（batch 256） | 408.96 s | 92.1 img/s | 12.61 | 10.3% | 7456 MB |
| **torch-GPU（batch 64）** | **356.09 s** | **105.8 img/s** | 12.45 | **25.0%** | 7708 MB |

**−12.9% 墙钟（+14.9% 吞吐）**，CPU 核数基本不变，GPU 利用率 10.3% → 25.0%，RSS +3.4%。

### 结论

- 喂料侧优化生效：单图预处理 17.9 → 3.7 ms，全量 −12.9%。
- 剩余优化空间：H2D 仍走 pageable（3.7 ms 中约 3 ms 是拷贝，换 pinned 可到 ~1.5 ms）；前向 2.9 ms/张（需确认 fp16 是否真正启用）；以及"前向空隙预取"。
- 全量测试索引已删除；结果保存在 `results/dual_path_full.json`。
